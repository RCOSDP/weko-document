# WEKO v2.0.4 から v2.1.0 へのアップデート方法

> **注記**: 本手順は、実装の差分（`git diff refs/tags/v2.0.4 origin/release_v2.1.0`、release_v2.1.0 は commit `508030789`／2026-09-30 時点）から作成したものであり、**実機では未検証**である。
> 確証の持てない手順・判断には **【要確認】** を付けている。【要確認】の箇所は、検証環境で確かめてから本番環境に適用すること。

## docker

本手順は、Docker Compose で構築した単一の WEKO 環境を、v2.0.4 から v2.1.0 へアップデートする場合を対象とする。

JAIRO Cloud 本番環境のような複数機関一括更新、Kubernetes、PgPool、Ingress Controller、fluentd 等のインフラ固有操作は対象外とする。AMS 用の nginx 設定（`nginx/weko-ams.conf`、`nginx/weko-ams-restricted.conf`、`nginx/Dockerfile.ams`）と arm64 用ファイル（`Dockerfile.arm64`、`docker-compose.arm64.yml` 等）も変更されているが、本手順では扱わない。

実際の環境によって以下は異なる可能性があるため、適宜読み替えること。

- Docker Compose ファイル名
- Docker Compose のサービス名
- PostgreSQL の DB 名
- Elasticsearch のインデックス prefix
- `instance.cfg` の環境固有設定
- nginx の `weko.conf` の環境固有設定
- Shibboleth や S3 等の外部連携設定

以下では Docker Compose ファイルを `docker-compose2.yml` とする。

## 1. アップデート前の状態を確認する

まず、現在の WEKO のブランチおよびコンテナ状態を確認する。

```bash
cd /path/to/weko

git status
git branch --show-current
git log -1 --oneline
git describe --tags
```

`v2.0.4` であることを確認する。

Docker の状態も確認する。

```bash
docker compose -f docker-compose2.yml ps
```

ローカルに未コミットの変更がある場合は、アップデート作業前にコミットまたは `git stash` 等で退避する。

### 1.1 item_type_mapping の重複・孤児行を確認する

v2.0.4 では、マッピングを保存するたびに `item_type_mapping` に行が追加されていた。v2.1.0 では 1 アイテムタイプにつき 1 行とし、一意制約と外部キーを追加する（10.3、10.4）。事前に件数を確認しておく。

重複行：

```bash
docker compose -f docker-compose2.yml exec postgresql \
  psql -U invenio invenio -c "
SELECT item_type_id, count(*) FROM item_type_mapping
 WHERE item_type_id IS NOT NULL
 GROUP BY item_type_id HAVING count(*) > 1;"
```

孤児行（存在しないアイテムタイプを指す行。外部キーを追加できない）：

```bash
docker compose -f docker-compose2.yml exec postgresql \
  psql -U invenio invenio -c "
SELECT m.id, m.item_type_id FROM item_type_mapping m
  LEFT JOIN item_type t ON m.item_type_id = t.id
 WHERE m.item_type_id IS NOT NULL AND t.id IS NULL;"
```

重複行は 10.3 のツールで解消する。孤児行が 1 件でもあると 10.4 の外部キー追加が失敗する。孤児行を解消するツールは v2.1.0 に含まれていないため、扱い（削除してよいか等）は個別に判断すること【要確認】。

### 1.2 グループが未設定のインデックスを確認する

v2.1.0 ではインデックスの閲覧・投稿の権限判定が「ロール判定 かつ グループ判定」に変わり、グループが未設定（空）のインデックスは、管理者以外の誰からも閲覧・投稿できなくなる。10.1 の SQL で既存インデックスを補正する。事前に対象件数を確認しておく。

```bash
docker compose -f docker-compose2.yml exec postgresql \
  psql -U invenio invenio -c "
SELECT count(*) FROM index
 WHERE is_deleted = false
   AND (browsing_group IS NULL OR browsing_group = ''
        OR contribute_group IS NULL OR contribute_group = '');"
```

### 1.3 alembic_version を確認する

```bash
docker compose -f docker-compose2.yml exec postgresql \
  psql -U invenio invenio -c "SELECT * FROM alembic_version;"
```

結果は 10.5 で使うため控えておく。

## 3. WEKO を停止する

データベースの更新中にデータ更新や外部からのアクセスが発生しないよう、WEKO Web、Celery worker、nginx を停止する。

```bash
docker compose -f docker-compose2.yml stop nginx web worker
```

環境全体を停止して問題ない場合は以下でもよい。

```bash
docker compose -f docker-compose2.yml down
```

ただし、後続手順では PostgreSQL コンテナと Web コンテナを起動して DB 更新を行う。

## 5. instance.cfg を確認する

| 設定キー | v2.0.4 | v2.1.0 | 内容 |
|---|---|---|---|
| `RECORDS_REST_DEFAULT_UPDATE_PERMISSION_FACTORY`（weko-deposit） | `None` | `deny_all` | REST による更新系操作の既定の権限判定 |

### 5.3 ログイン API のレート制限

v2.1.0 では、REST API のログイン（`WEKO_ACCOUNTS_REST_ENDPOINTS` の `login`）にレート制限が有効になった。制限値は既存の設定キー `WEKO_API_LIMIT_RATE_DEFAULT`（既定 `['100 per minute']`）を使用する。キーは「エンドポイント＋接続元アドレス」で、接続元アドレスの取り方は既存の `WEKO_ACCOUNTS_REAL_IP` に従う。

あわせて、ログイン API の失敗応答が統一された（メールアドレス・パスワードの誤りは 403 `Invalid email or password.`、不正なリクエスト本文は 400）。ログイン API を利用する外部システムがある場合は、エラー応答の扱いを確認すること。

### 5.4 S3 読み取り専用アクセスキー（#61752）

S3 読み取り専用アクセスキー（`S3_READONLY_ACCESS_KEY_ID`、`S3_READONLY_SECRET_ACCESS_KEY`、`files_location.readonly_access_key` 等）は v2.0.4 の時点で取り込み済みであり、v2.0.4 から v2.1.0 への更新で追加の作業はない。

## 6. nginx の設定を確認する

nginx の設定は `nginx/Dockerfile` で nginx イメージに組み込まれる（`ADD weko.conf /etc/nginx/conf.d/`）。v2.1.0 の変更を反映するため、`nginx/weko.conf` を確認したうえで nginx イメージを再ビルドする（8）。

### 6.1 Shibboleth SP 属性の受け付け元の限定

v2.1.0 では、Shibboleth SP の属性を `/weko/shib/login` へ POST できる送信元を、Web サーバ上のログインスクリプト（`secure/login.py`）に限定した（`login.php` は v2.1.0 で削除された。6.4 参照）。

- WEKO 側: `WEKO_ACCOUNTS_SHIB_SP_ALLOWED_ADDRS`（既定 `127.0.0.1`、`::1`）以外の送信元からの POST は 403 になる
- ログインスクリプト側: POST 先をループバックアドレス（`<scheme>://127.0.0.1/weko/shib/login`）にし、`Host` ヘッダに公開ホスト名を入れる
- nginx 側: `/weko/shib/login` への GET・HEAD 以外は、接続元がループバックアドレスの場合のみ許可する

**ログインスクリプトと nginx の設定は同時に更新すること。どちらか一方だけでは Shibboleth ログインが通らなくなる。**

`weko.conf` の追加箇所は以下。

```nginx
# POST to /weko/shib/login is allowed only from the loopback address of the
# connection (see location = /weko/shib/login).
map "$request_method:$realip_remote_addr" $weko_shib_sp_denied {
	default          1;
	"~^(GET|HEAD):"  0;
	"POST:127.0.0.1" 0;
	"POST:::1"       0;
}
```

```nginx
	location = /weko/shib/login {
		if ($weko_shib_sp_denied) {
			return 403;
		}
		uwsgi_pass app_server;
		include uwsgi_params;
		uwsgi_param REMOTE_ADDR $realip_remote_addr;

		uwsgi_buffering off;
		uwsgi_request_buffering off;

		uwsgi_buffer_size 32k;
		uwsgi_buffers 8 32k;
		uwsgi_busy_buffers_size 32k;

		uwsgi_param Host $host;
		uwsgi_param X-Forwarded-For $proxy_add_x_forwarded_for;
		uwsgi_param X-Forwarded-Proto $scheme;
	}
```

判定には `$realip_remote_addr`（real_ip モジュールで `X-Forwarded-For` により書き換える前の接続元アドレス）を使用し、WEKO に渡す `REMOTE_ADDR` も同じ値にする。これは、信頼するプロキシとして設定したアドレスから `X-Forwarded-For` にループバックアドレスを入れた要求を通さないためである。

リポジトリの `nginx/weko.conf` には `set_real_ip_from` / `real_ip_header` の設定は含まれていない。前段にロードバランサ等を置いて real_ip を設定している環境では、上記の判定が接続元（前段のプロキシ）のアドレスで行われることを確認すること。

前段のプロキシや別ホストからログインスクリプトを動かす構成で、WEKO に届く送信元がループバックアドレスにならない場合は、`WEKO_ACCOUNTS_SHIB_SP_ALLOWED_ADDRS` と nginx の `map` の両方を環境に合わせて変更する必要がある【要確認】。

Shibboleth を使用していない Docker 環境でも、`weko.conf` の追加は影響しない（GET・HEAD は従来どおり通る）。

### 6.2 gzip

`weko.conf` の gzip 設定が以下のとおり変更された。

```diff
-	gzip_http_version 1.1;
+	gzip_http_version 1.0; # 前段のプロキシは既定で HTTP/1.0 で転送してくる
```

```diff
 		application/manifest+json
-		application/octet-stream
 		application/rss+xml
```

```diff
 		text/css
-		text/html
 		text/javascript
```

- 前段のプロキシから HTTP/1.0 で転送されたリクエストにも gzip を適用する
- バイナリのダウンロード（`application/octet-stream`）を gzip の対象から外す

### 6.3 listen 443 ssl

非推奨の `ssl on;` を `listen` の `ssl` 指定に置き換えた。

```diff
-	listen 443;
-	ssl on;
+	listen 443 ssl;
```

### 6.4 nginx イメージ（nginx/Dockerfile）の変更

v2.1.0 では、nginx イメージが次のように変わった（PR #1936 を含む）。

- **Shibboleth のログインスクリプトを `login.py` に統一した**
  - `/usr/share/nginx/html/secure/login.py` を配置し、`fcgiwrap` で実行する（`weko.conf` の `location ~ /secure/`）。WEKO 側のログイン URL `WEKO_ACCOUNTS_SHIB_IDP_LOGIN_URL` の既定値も `'{}secure/login.py'` である。
  - `login.py` が使う `requests` は、apt の `python3-requests` で導入する（`python3-pip` と `pip3 install requests` は使わない）。
- **PHP を削除した**（`login.php` による運用は終了している）
  - `php-fpm`、`php-curl` をインストールしない。php-fpm の設定書き換えも行わない。
  - `nginx/supervisord.conf` から `[program:php-fpm]` を削除した。
  - `nginx/weko-ams.conf`、`nginx/weko-ams-restricted.conf` から `.php` 用の `location` を削除した。`nginx/weko.conf` のコメントアウトされていた同じ `location` も削除した。
  - `nginx/login.php`、`nginx/index.php`、`nginx/phpinfo.php` を削除した。
- **arm64 で Shibboleth の認可プロセスが起動するようにした**
  - `nginx/supervisord.conf` は shibauthorizer・shibresponder を `/usr/lib/x86_64-linux-gnu/shibboleth/` から起動するよう書かれている。arm64 では実体が `/usr/lib/aarch64-linux-gnu/shibboleth/` にあるため、従来は起動できず Shibboleth でログインできなかった。
  - v2.1.0 では、ビルド時に `uname -m` でこのパスを実行環境のアーキテクチャに合わせて書き換える（x86_64 では変わらない）。
  - `nginx/Dockerfile.arm64` は `nginx/Dockerfile` と同じ内容になった。
  - AMS 用の `nginx/Dockerfile.ams` も arm64 でビルドできるようにした（x86_64 専用の pagespeed モジュールを組み込まない、`.deb` をワイルドカードで取得する、上記のパスの書き換え）。
- **その他**
  - `RUN` を連結して整理し、ビルドした `.deb` をアーキテクチャ名のワイルドカード（`nginx_1.20.1-1~focal_*.deb`）で取得するようにした。
  - pagespeed モジュール（`incubator-pagespeed-ngx`）を組み込まなくなった。

取得したソースに上記の変更が入っていることを確認する。次のコマンドで `login.py` の行（`ADD ./login.py` と `RUN chmod 755 .../login.py` の2行）だけが表示され、`login.php` や `php-fpm` を含む行が表示されなければよい。

```bash
grep -n 'login\.\|php-fpm' nginx/Dockerfile
```

`login.php` や `php-fpm` が表示される場合は、PR #1936 が取り込まれる前のソースである。この場合は、PR #1936 が取り込まれたソースを取得し直してからビルドすること。

環境固有に nginx の設定を変更している場合は、次の点を確認する。

- `weko.conf` などに `.php` 用の `location` を残していても、`.php` ファイルは配置されないので動作に影響はない。ただし php-fpm のソケットも存在しないため、削除しておくことを推奨する。
- `WEKO_ACCOUNTS_SHIB_IDP_LOGIN_URL` を `secure/login.php` に変更している場合は、`secure/login.py` に戻す。

nginx イメージを再ビルドした後（8）、ログインスクリプトと必要なプロセスがそろっていることを確認する。

```bash

  sh -c 'ls -l /usr/share/nginx/html/secure/ && which fcgiwrap && python3 -c "import requests"'
```


`shibd`、`shibauthorizer`、`shibresponder`、`fcgiwrap`、`nginx` が `RUNNING` であればよい（`php-fpm` は表示されない）。

`weko.conf` で pagespeed のディレクティブを使用していないことも確認する（リポジトリの `weko.conf` では使用していない）。


### 10.1 W2025-61a.sql（インデックスのグループ）

v2.1.0 では、インデックスの閲覧・投稿の権限判定が「ロール判定 かつ グループ判定」に変わった。グループ判定では、どのグループにも属していないユーザ（未ログインを含む）を「グループなし」（ID `-89`）として扱う。このため、グループが未設定のインデックスは管理者以外から閲覧・投稿できなくなる。

`W2025-61a.sql` は、削除されていない全インデックス（`is_deleted = false`）について、`browsing_group` と `contribute_group` を以下のように更新する。

- 空（NULL または `''`）の場合は `'-89'` にする
- すでに `-89` を含む場合は変更しない
- それ以外は末尾に `,-89` を追加する

すでに `-89` を含む値は変更しないため、再実行しても結果は変わらない。処理は 1 つの `DO` ブロックで実行される。

SQL ファイルを PostgreSQL コンテナへコピーする。

```bash
docker cp \
  postgresql/ddl/W2025-61a.sql \
  $(docker compose -f docker-compose2.yml ps -q postgresql):/tmp/W2025-61a.sql
```

実行する。

```bash
docker compose -f docker-compose2.yml exec postgresql \
  psql -U invenio invenio \
  -f /tmp/W2025-61a.sql \
  2>&1 | tee migration_W2025-61a.log
```

`NOTICE:  Start: W2025-61a.sql` と `NOTICE:  Update completed.` が出力されることを確認する。

```bash
grep -i error migration_W2025-61a.log
```

**注意【要確認】**: v2.1.0 のグループ判定では、いずれかのグループ（またはグループ用ロール）に属するログインユーザには「グループなし」（`-89`）が付与されない。このため、本 SQL でグループが `'-89'` のみになったインデックスは、何らかのグループに属するユーザからは閲覧・投稿できない可能性がある。グループを利用している環境では、更新後にインデックスの閲覧・投稿グループの設定を確認すること（15 の動作確認を参照）。

v2.1.0 で新規に作成するインデックスには、既定で全グループと「グループなし」（`-89`）が設定される。

### 10.3 migrate_item_type_mapping.py（item_type_mapping の重複解消）

v2.0.4 ではマッピングの保存のたびに `item_type_mapping` に行が追加されていたが、v2.1.0 では 1 アイテムタイプ 1 行として更新する。既存の重複行をまとめるため、`tools/update/migrate_item_type_mapping.py` を実行する。

```bash
docker compose -f docker-compose2.yml exec web \
  invenio shell tools/update/migrate_item_type_mapping.py \
  2>&1 | tee migration_item_type_mapping.log
```

ツールの処理内容は以下。

- 重複行（同じ `item_type_id` の行が複数）が無い場合は `Not need to migrate item_type_mapping.` を出力して終了する（再実行しても問題ない）
- 重複行がある場合は、`item_type_mapping` とその履歴テーブル（`item_type_mapping_version`）を一時テーブル（`*_tmp`）に複製したうえで両テーブルを TRUNCATE し、一時テーブルの行を `id` の昇順に読み直して、`item_type_id` ごとに 1 行へ作成・上書きする。結果として、各アイテムタイプについて `id` が最も大きい行のマッピングが残る
- `created` / `updated` は元の値を引き継ぐ。行の `id` は振り直される
- 履歴テーブル（`item_type_mapping_version`）の過去の履歴は、移行で作成し直したもののみになる
- 途中で失敗した場合は、一時テーブルから元のデータに戻し、一時テーブルを削除する

`Migration completed at ...` が出力されることを確認し、1.1 の重複行確認の SQL で重複が無くなったことを確認する。

一時テーブルが残っている場合（前回の実行が異常終了した等）、ツールは `Temporary table for migration already exists.` を出力して処理しない。その場合は `recovery` 引数を付けて実行し、一時テーブルからデータを戻す。

```bash
docker compose -f docker-compose2.yml exec web \
  invenio shell tools/update/migrate_item_type_mapping.py recovery
```

### 10.4 W2025-16.sql（item_type_mapping の制約追加）

`W2025-16.sql` は以下を行う。

- `item_type_mapping.item_type_id` に一意制約 `uq_item_type_mapping_item_type_id` を追加
- `item_type_mapping.item_type_id` に `item_type.id` を参照する外部キー `fk_item_type_mapping_item_type_id_item_type`（`ON DELETE CASCADE`）を追加
- 不要になったインデックス `idx_created_item_type_mapping`、`idx_item_type_id_item_type_mapping` を削除（`IF EXISTS`）

制約の追加は `IF NOT EXISTS` を伴わないため、**再実行すると「already exists」のエラーになる**。また、トランザクションで囲まれていないため、途中で失敗すると一部だけが適用された状態になる。必要に応じて `psql` の `--single-transaction` と `-v ON_ERROR_STOP=1` を指定して実行する。

SQL ファイルを PostgreSQL コンテナへコピーする。

```bash
docker cp \
  postgresql/update/W2025-16.sql \
  $(docker compose -f docker-compose2.yml ps -q postgresql):/tmp/W2025-16.sql
```

実行する。

```bash
docker compose -f docker-compose2.yml exec postgresql \
  psql -U invenio invenio \
  --single-transaction -v ON_ERROR_STOP=1 \
  -f /tmp/W2025-16.sql \
  2>&1 | tee migration_W2025-16.log
```

エラー確認：

```bash
grep -i error migration_W2025-16.log
```

制約が追加されたことを確認する。

```bash
docker compose -f docker-compose2.yml exec postgresql \
  psql -U invenio invenio -c "\d item_type_mapping"
```

`uq_item_type_mapping_item_type_id`（UNIQUE）と `fk_item_type_mapping_item_type_id_item_type`（FOREIGN KEY）が表示されることを確認する。

`could not create unique index` のエラーになった場合は重複行が残っている（10.3 を確認）。`violates foreign key constraint` のエラーになった場合は孤児行がある（1.1 を確認）。

**補足【要確認】**: v2.1.0 の `ItemTypeMapping` モデルには GIN インデックス `idx_mapping_item_type_mapping`（`mapping` 列、`USING gin`）が定義されているが、`W2025-16.sql` と Alembic リビジョンのいずれにも作成処理は含まれていない。既存 DB にはこのインデックスは作成されない。作成の要否は確認が必要。

### 10.5 alembic_version の扱い【要確認】

v2.1.0 では、全モジュールの Alembic 履歴が新しい基準リビジョンへ再編された（#61275）。

- WEKO 系モジュール（weko-admin、weko-authors、weko-gridlayout、weko-groups、weko-index-tree、weko-indextree-journal、weko-items-ui、weko-logging、weko-notifications、weko-records、weko-records-ui、weko-swordserver、weko-user-profiles、weko-workflow、weko-workspace）の既存リビジョンは削除され、各ブランチは処理を持たない新しい基準リビジョン（`down_revision = None`、`upgrade()` は `pass`）1 つに置き換わった
- weko-accounts に基準リビジョン（`a8e506eb5e32`）が新設された
- weko-records にのみ、新しい基準リビジョン（`32ecd938a01b`）に続くリビジョン `e0dd9fb514cf`（`add_constraints_to_mapping`）がある。処理内容は 10.4 の `W2025-16.sql` と同じ（一意制約・外部キーの追加とインデックスの削除）
- invenio-accounts（`b5c2d8a5bf90`）、invenio-files-rest（`8644b32a3eec`）、invenio-mail（`ddbb24276fdc`、`b1495e98969b`）の WEKO 独自リビジョンが削除された
- invenio-oaiharvester、invenio-resourcesyncclient、invenio-resourcesyncserver の `alembic` ディレクトリ内のリビジョンは無くなった（ファイルは他モジュールへ移動）が、各 `setup.py` の `invenio_db.alembic` エントリポイントは残っている。weko-schema-ui には `invenio_db.alembic` エントリポイントが追加されたが、`alembic` ディレクトリは存在しない

v2.0.4 で `invenio db create` により作成した DB の `alembic_version` には、作成時点の各ブランチの head（例: `f312b8c2839a`、`8644b32a3eec`、`b1495e98969b` 等）が記録されている（`invenio db create` は `alembic_version` が無ければ全 head で stamp する）。これらのリビジョンは v2.1.0 には存在しないため、v2.1.0 で `invenio alembic upgrade` 等の Alembic コマンドを実行すると、記録済みリビジョンを解決できずに失敗すると考えられる【要確認】。

本手順では、スキーマ変更を 10.4 の SQL（`W2025-16.sql`）で適用し、`invenio alembic upgrade` は実行しない。今後 Alembic を利用する場合は、`alembic_version` を v2.1.0 のリビジョンに合わせる必要があるが、その手順は実装・ドキュメントで示されていない【要確認】。考えられる方法は以下であるが、実機で未確認である。

```bash
# 【要確認】実機未検証。必ずバックアップ後、検証環境で確認すること
docker compose -f docker-compose2.yml exec postgresql \
  psql -U invenio invenio -c "DELETE FROM alembic_version;"

docker compose -f docker-compose2.yml exec web \
  invenio alembic stamp
```

`invenio alembic stamp`（Flask-Alembic）は既定で全 head（weko-records は `e0dd9fb514cf`）を記録する。10.4 を適用済みの DB に対して `e0dd9fb514cf` まで記録されることになる。上記のとおり `alembic` ディレクトリが存在しないエントリポイントがあるため、Alembic コマンド自体が失敗する可能性もある【要確認】。

確認：

```bash
docker compose -f docker-compose2.yml exec postgresql \
  psql -U invenio invenio -c "SELECT * FROM alembic_version;"
```

## 18. 切り戻し

アップデートに失敗した場合は、v2.0.4 のソースと 2 で取得したバックアップに戻す。

10.1、10.3、10.4、10.6 の DB 更新には、元に戻すための SQL・ツールは用意されていない（10.3 の `recovery` は、ツールの実行中に失敗した場合の復旧用であり、完了後の切り戻しには使えない）。DB は 2.1 のバックアップから復元する。

WEKO を停止する。

```bash
docker compose -f docker-compose2.yml stop nginx web worker
```

ソースを v2.0.4 に戻す。

```bash
git checkout v2.0.4
```

2.2 で退避した設定ファイル（`nginx/weko.conf`、`nginx/login.py`、`nginx/login.php` 等）を必要に応じて戻し、イメージを再ビルドする。

```bash
docker compose -f docker-compose2.yml build
```

DB をバックアップから復元する。既存の DB を削除して作り直したうえで、2.1 のダンプを投入する。

```bash
docker compose -f docker-compose2.yml exec postgresql \
  dropdb -U invenio invenio

docker compose -f docker-compose2.yml exec postgresql \
  createdb -U invenio -O invenio invenio

docker compose -f docker-compose2.yml exec -T postgresql \
  psql -U invenio invenio \
  < weko_v2.0.4_before_upgrade.sql
```

DB 名・ユーザー名・所有者は環境に合わせて読み替えること。DB への接続が残っていると `dropdb` が失敗するため、Web / worker 等を停止した状態で行う。

static assets を戻し、起動する。

```bash
docker compose -f docker-compose2.yml up -d
docker compose -f docker-compose2.yml exec web invenio assets build
docker compose -f docker-compose2.yml exec web invenio collect
```

v2.1.0 への更新後に登録・更新したアイテムがある場合、DB はバックアップ時点に戻るが、Elasticsearch のインデックスには更新後の内容が残る。その場合は再インデックス等で DB と Elasticsearch の内容を揃える必要がある。

# 補足

## 要確認事項の一覧

| 箇所 | 内容 |
|---|---|
| 1.1 | 孤児行（存在しないアイテムタイプを指す `item_type_mapping` の行）の扱い |
| 6.1 | 前段にプロキシを置く構成での、Shibboleth SP 属性の受け付け元の設定 |
| 10.1 | `-89` のみになったインデックスを、グループに属するユーザが参照できるか |
| 10.4 | GIN インデックス `idx_mapping_item_type_mapping` の作成要否 |
| 10.5 | 既存 DB の `alembic_version` の扱い（削除・stamp の要否と手順、`alembic` ディレクトリの無いエントリポイントの影響） |
| 11 | `WEKO_SEARCH_FIX_ACCESSRIGHTS` を有効にした場合の再インデックスの要否 |
| 14.1 | 既存のアクセストークンに `item:bulkprocess` を付与する方法（発行し直しの要否） |

## 対象外とした処理

JAIRO Cloud 本番環境のような構成では、以下の処理が別途必要になる可能性がある。

- PgPool、Ingress Controller、NGINX Plus 等の前段の設定変更（real_ip の設定を含む）
- 複数リポジトリ一括処理
- Kubernetes Pod 単位の処理
- AMS（`nginx/weko-ams.conf`、`nginx/weko-ams-restricted.conf`）の更新

これらは WEKO v2.1.0 の単一 Docker 環境におけるアプリケーション更新そのものではないため、本手順では対象外とする。
