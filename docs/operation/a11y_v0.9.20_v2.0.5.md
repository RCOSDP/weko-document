# 読書バリアフリー（feature/a11y）から WEKO v2.0.5 へのアップデート方法

> **注記**: 本手順は、実装の差分から作成した。比較したのは `origin/feature/a11y_pre`（commit `9d545650b`）と `origin/develop_v2.0.5`（commit `96f87e167`／2026-10-30 時点）である。**実機では未検証**である。
> 移行ツールの SQL は、使い捨ての PostgreSQL 12 で 2 種類のスキーマに流して確かめた。1 つは v2.0.5 のスキーマ、もう 1 つは旧形式を模したテーブルである。どちらでも意図した結果になり、2 回流しても結果が変わらないことを確認した。
> 一方、旧環境の実データでの通し確認はしていない。確証の持てない手順・判断には **【要確認】** を付けた。【要確認】の箇所は、本番のデータを複製した検証環境で確かめてから本番環境に適用すること。

読書バリアフリー資料メタデータ共有システム（以下、読バリ）は、feature/a11y ブランチのコードで動いている。構築の経緯は [a11y構築手順](a11y構築手順.md) を参照すること。
feature/a11y は `release` ブランチの 2022-09-27 時点（v0.9.20 と v0.9.20a の間）から分かれたブランチである。そのため本手順では、v0.9.20 相当から v2.0.5 までの変更をまとめて適用する。
読バリ固有の変更（アクセシビリティ対応）は、v2.0.5 のコードに取り込んだうえで `feature/a11y_pre` ブランチに用意する前提とする。

本手順で使う移行ツールは、WEKO リポジトリの `tools/migration/v2.0.5/` にある。使い方の詳細はツールの README を参照すること。

| ツール | 内容 |
|---|---|
| `migrate.sh` | PostgreSQL・Elasticsearch・静的ファイルの移行を、決まった順番で実行する。1 回しか実行してはいけない処理は DB に記録し、再実行時には飛ばす |
| `migrate_config.py` | `instance.cfg` をキー単位でマージする。nginx の設定などは 3-way マージする。環境変数の不足も確認する |

## 0. v2.0.5 での主な変更点（運用に関係するもの）

| 区分 | 内容 | 本手順での対応 |
|---|---|---|
| DB（スキーマ） | v0.9.20 から v1.0.8 までの列追加・型変更（`files_location`、`facet_search_setting`、`mail_config`、`shibboleth_user` ほか） | 8（`db.10`） |
| DB（データ） | アイテムタイプのプロパティの更新（v0.9.27 の `update_v0927()`、JPCOAR 2.0 対応） | 8（`db.20`〜`db.25`） |
| DB（データ） | 既定アイテムタイプの ID の付け替え（15 → 30002、16 → 30001。`fix_itemtype_issue_45614`） | 8（`db.30`） |
| DB（スキーマ・データ） | v1.0.8 から v2.0 への一括移行（`postgresql/ddl/W2025-29.sql`。メールテンプレートの DB 化、制限公開、著者とコミュニティの関連、ユーザ操作ログなど） | 8（`db.40`〜`db.42`） |
| DB（スキーマ） | `stats_events` を月ごとのパーティションテーブルへ変更 | 8（`db.50`、`db.51`） |
| DB（データ） | `update_W2025-29.py` によるメタデータとアイテムタイプの変換 | 8（`db.60`） |
| Elasticsearch | イメージを OSS 版から既定ディストリビューションへ変更（ILM を使うため） | 7 |
| Elasticsearch | 統計を ILM のロールオーバーで書き込む方式へ変更。書き込み先として `-000001` インデックスが必要 | 9 |
| Elasticsearch | 著者インデックスに `communityIds` を追加。アイテムの文書の内容も変わったため、全件の再インデックスが必要 | 9 |
| 設定 | `instance.cfg` の設定項目が 88 から 192 に増えた。シークレットは環境変数から読む方式に変わった | 3 |
| 設定 | web と worker のコンテナを分離した。pgpool・mongo・inbox を追加した | 3.4 |
| nginx | `login.php` を `login.py`（fcgiwrap）に置き換えた。inbox への経路と `/secure/` の設定を変えた | 3.3 |

## 1. アップデート前の状態を確認する

稼働中の環境で、移行ツールの事前確認を実行する。この確認は読み取りだけで、DB は変更しない。
旧環境（feature/a11y のコード）の Pod でも実行できる。

ツールは、v2.0.5 のコードをチェックアウトしたホストから実行する。チェックアウトするのは、移行ツールを含む `feature/a11y_pre` 系のブランチである。

```bash
git clone https://github.com/RCOSDP/weko.git weko-v2.0.5
cd weko-v2.0.5
git checkout <v2.0.5 ベースの a11y ブランチ>
```

web コンテナと psql を呼ぶコマンドは、環境変数で指定する。

docker compose の場合：

```bash
export WEKO_MIG_WEB="docker compose -f docker-compose2.yml exec -T web"
export WEKO_MIG_PSQL="docker compose -f docker-compose2.yml exec -T postgresql psql -U invenio invenio"
```

Kubernetes の場合（DB は更新系の Pod を指定する）：

```bash
FQDN=a11y.pub.repo.nii.ac.jp
DBNAME=$(echo $FQDN | tr "." "_" | tr "-" "_")
POD=$(kubectl get pods -n weko3 | grep ^$(echo $DBNAME | tr "_" "-") | cut -d' ' -f 1)
DB_POD=$(kubectl get pods -l application=spilo,spilo-role=master -n weko3pg -o name | head -1)
export WEKO_MIG_WEB="kubectl exec -i -n weko3 ${POD} -c web --"
export WEKO_MIG_PSQL="kubectl exec -i -n weko3pg ${DB_POD#pod/} -- psql -U invenio ${DBNAME}"
```

DB 名の付け方と Pod の探し方は、[v1.0.7 から v1.0.7b へのアップデート方法](v1.0.7_to_v1.0.7b.md) に合わせた。実際の名前は環境に合わせて読み替えること【要確認】。

共通の設定：

```bash
export WEKO_MIG_INDEX_PREFIX=<SEARCH_INDEX_PREFIX の値>
export WEKO_MIG_CODE=$(pwd)
export WEKO_MIG_LOG_DIR=$(pwd)/upgrade-logs-$(date +%Y%m%d)
```

事前確認を実行する。

```bash
tools/migration/v2.0.5/migrate.sh preflight
```

結果は `${WEKO_MIG_LOG_DIR}/preflight-*.txt` に保存される。以下を確認する。

| 項目 | 確認すること | 問題があった場合 |
|---|---|---|
| owner が数値でないレコード | 0 件であること | `W2025-29.sql` は owner を数値に変換するため、1 件でもあると移行全体が失敗する。該当レコードの owner を直してから進める |
| 完了していないアクティビティ | 0 件であること | 移行ではアクティビティの一時データ（`temp_data`）を変換しない。完了または取り消しを済ませてから進める |
| `file_onetime_download` の件数 | 件数を記録する | `W2025-29.sql` はこのテーブルを作り直すため、ワンタイムダウンロードの発行履歴は消える |
| `stats_events` | 件数と最古・最新の日付を記録する | 移行後の件数と比べる |
| `item_type` 15/16/30001/30002 | どれがあるか記録する | 読バリが使うのは独自アイテムタイプ（ID 21）。既定アイテムタイプが無い場合、移行ツールはその ID 用の JSON-LD マッピングを作らない |
| `sitelicense_ip_address` の主キー | 列の構成を記録する | 移行ツールが `(organization_id, organization_no)` に変更する |
| 件数の一覧 | 記録する | 移行後の 12 で比べる |

## 2. バックアップを取得する

アップデート前に、少なくとも次の 4 つをバックアップする。Elasticsearch は、7 でイメージを切り替えると OSS 版に戻せなくなるため、必ずスナップショットを取ること。

### 2.1 PostgreSQL

```bash
kubectl exec -n weko3pg ${DB_POD#pod/} -- pg_dump -U invenio -Fc ${DBNAME} \
  > weko_a11y_before_v2.0.5.dump
```

docker compose の場合：

```bash
docker compose -f docker-compose2.yml exec -T postgresql \
  pg_dump -U invenio -Fc invenio > weko_a11y_before_v2.0.5.dump
```

### 2.2 Elasticsearch

スナップショットの保存先は、Elasticsearch の `path.repo` に設定したディレクトリにする。

```bash
${WEKO_MIG_WEB} curl -XPUT "http://elasticsearch:9200/_snapshot/before_v205" \
  -H 'Content-Type: application/json' \
  -d '{"type":"fs","settings":{"location":"/usr/share/elasticsearch/backups"}}'
${WEKO_MIG_WEB} curl -XPUT \
  "http://elasticsearch:9200/_snapshot/before_v205/snapshot_1?wait_for_completion=true" \
  -H 'Content-Type: application/json' \
  -d '{"indices":"'${WEKO_MIG_INDEX_PREFIX}'-*","include_global_state":false}'
```

docker compose の構成では、`/usr/share/elasticsearch/backups` はボリュームになっていない。`docker cp` でホストへ取り出しておくこと。
Kubernetes の Elasticsearch が複数機関で共用されている場合は、スナップショットの保存先と取得範囲を運用担当と相談すること【要確認】。

### 2.3 ファイルストレージ

アイテムのファイルを保存しているボリューム（`/var/tmp`。docker compose では `weko3_data`）をバックアップする。v2.0.5 でもファイルの置き場所は変わらず、移動は不要である。

### 2.4 設定ファイル

次のファイルを退避する。3 で、これらを v2.0.5 用にマージする。

- `instance.cfg`（Kubernetes では ConfigMap に入っているもの）
- ConfigMap と Secret のマニフェスト（`configmap.yaml`、`secret.yaml`、`deploy-web.yaml`）
- nginx のイメージに入れている `weko.conf`、`nginx.conf`、`shibboleth2.xml`、`login.php`、証明書
- docker compose の場合は `docker-compose2.yml` と `.env`

## 3. 設定ファイルを v2.0.5 用に更新する

この作業は、停止前に済ませておける。

### 3.1 instance.cfg

サイトの `instance.cfg` を、v2.0.5 の `scripts/instance.cfg` とキー単位でマージする。

```bash
python3 tools/migration/v2.0.5/migrate_config.py instance-cfg \
  --repo . --site backup/instance.cfg --out instance.cfg.v2.0.5
```

マージは次の規則で行う。

- **サイトが変えたキー**（旧コードの値と違うキー）は、サイトの値を残す。
- **サイトが変えていないキー**は、v2.0.5 の値にする。
- **v2.0.5 にないキー**は、ファイルの末尾に追加する。

ツールは、判断が必要な箇所を 3 段階で出力する。

| 段階 | 意味 |
|---|---|
| `ACTION` | 対応が必要 |
| `WARN` | 確認が必要 |
| `INFO` | 参考 |

読バリについて確認が必要な点は次のとおりである。

| キー | v2.0.5 での変化 | 読バリでの扱い |
|---|---|---|
| `WEKO_ACCOUNTS_SHIB_LOGIN_ENABLED` | 既定値が `False` になった。v2.0.5 は起動時にこの値で DB の `shib_login_enable` を上書きする | 読バリはローカル認証なので `False` のままでよい（サイトの値が残る） |
| `SECURITY_REGISTERABLE` | 既定値が `False` になった | 読バリは `False` に設定している。値は変わらない |
| `SECURITY_RECOVERABLE` | モジュールの既定値が `True` から `False` になった。メールによるパスワード再設定ができなくなる | 読バリはローカル認証なので、パスワード再設定を残すなら `SECURITY_RECOVERABLE = True` を追記する【要確認】 |
| `WEKO_SHOW_INDEX_FOR_AUTHENTICATED_USER` | v2.0.5 の `instance.cfg` には無い（モジュールの設定として残っている） | ツールが末尾に追加する |
| `THEME_LOGO`、`THEME_LOGO_ADMIN` | 既定のロゴが JAIRO Cloud のものになった | 読バリのロゴを使っている場合は値を確認する |
| `WEKO_WORKFLOW_ACCESS_ACTIVITY_URL`、`WEKO_WORKFLOW_REQUEST_FOR_REGISTER_USAGE_REPORT` | `.tpl` のファイル名から、DB のメールテンプレートの ID に変わった | 旧版でテンプレートを変えていた場合は、管理画面のメールテンプレートに移す |
| `WEKO_ITEMS_UI_CRIS_LINKAGE_RESEARCHMAP_*` | 既定値が researchmap の試験用 API を指す | researchmap 連携を使わないなら、そのままでよい |
| `WEKO_NOTIFICATIONS_INBOX_ADDRESS` | inbox サービスのアドレス | 3.4 の inbox の構成に合わせる |
| `S3_ACCCESS_KEY_ID`、`S3_SECRECT_ACCESS_KEY` | 綴りを間違えたキー。`invenio_s3` は、このキーが定義されているだけで正しいキーを上書きする | ツールが削除し、値を正しいキーに移す |

### 3.2 環境変数（ConfigMap / Secret）

v2.0.5 の `instance.cfg` は、シークレットや Redis の DB 番号を環境変数から読む。
環境変数が足りないと、jinja2 はその値を文字列 `None` として描画する。たとえば `SECRET_KEY` は `'None'` になる。

マージした `instance.cfg` を entrypoint と同じように描画して、確認する。

```bash
python3 tools/migration/v2.0.5/migrate_config.py check-env \
  --cfg instance.cfg.v2.0.5 --env backup/configmap.yaml --env backup/secret.yaml
```

Secret の `data` は base64 のままでは読めない。`stringData` に書き直したファイルか、`KEY=VALUE` 形式に直したファイルを渡すこと。

新たに必要になる主な環境変数は次のとおりである。

| 環境変数 | 内容 |
|---|---|
| `SECRET_KEY`、`WTF_CSRF_SECRET_KEY`、`WEKO_RECORDS_UI_SECRET_KEY` | 旧版の `instance.cfg` に直接書いていた値を移す。値に `'` を含めないこと（描画後の Python が壊れる） |
| `CACHE_REDIS_DB`、`ACCOUNTS_SESSION_REDIS_DB_NO`、`CELERY_RESULT_BACKEND_DB_NO` | Redis の DB 番号 |
| `WEKO_AGGREGATE_EVENT_HOUR`、`WEKO_AGGREGATE_EVENT_MINUTE` | 統計の集計を実行する時刻 |
| `WEKO_HANDLE_ALLOW_REGISTER_CRNI` | CNRI ハンドルを登録するか（`True` / `False`）。環境変数名の綴りは CRNI のまま |
| `TIKA_JAR_FILE_PATH` | ファイル本文の抽出に使う Tika。無いとアイテムのファイルの全文抽出が失敗する |
| `INVENIO_WEB_PROTOCOL`、`INVENIO_WEB_HOST_NAME` | worker でも必須 |

v2.0.5 の docker-compose では、worker にシークレットの環境変数が渡されていない。
一方で、web と worker は同じボリュームの `invenio.cfg` を描画する。後から起動した側の内容が残るので、**web と worker には同じ環境変数を渡すこと**。

### 3.3 nginx

nginx の設定ファイルはイメージに焼き込まれるため、変更後は nginx イメージをビルドし直す。
サイトのファイルと v2.0.5 のファイルを 3-way マージする。

```bash
for f in nginx/weko.conf nginx/nginx.conf nginx/shibboleth2.xml nginx/Dockerfile; do
  python3 tools/migration/v2.0.5/migrate_config.py merge \
    --repo . --path $f --site backup/$(basename $f) --out $f
done
```

衝突があれば、`<<<<<<< site`〜`>>>>>>> v2.0.5` のマーカーが残る。手で解消すること。

v2.0.5 で取り込む必要がある構造上の変更：

- `upstream inbox_server` と `/inbox` の location を追加。
- `/secure` を php-fpm から fcgiwrap の `login.py` へ変更。
- `/data` の `proxy_cache` を追加。これに伴い、`nginx.conf` に `proxy_cache_path` が必要になる。

`login.php` に加えたカスタマイズは `login.py` に自動では移らないので、手で移植する。読バリは Shibboleth を使っていないので、通常は不要である。

### 3.4 コンテナ構成（docker-compose2.yml / Kubernetes マニフェスト）

docker compose の場合は、`docker-compose2.yml` も同じく 3-way マージする（`--path docker-compose2.yml`）。
Kubernetes の場合は、`deploy-web.yaml` を次の点に合わせて直す【要確認】。

- web と worker を分ける。web は uwsgi だけ、worker は celery worker と celery beat を動かす（`scripts/supervisord_web.conf`、`scripts/supervisord_worker.conf`）。
  - 旧版のように web で `celery -B` を動かしたままにすると、beat が二重に起動する。
- DB への接続は pgpool 経由になった（`INVENIO_POSTGRESQL_HOST`）。
- 一時ディレクトリは `TMPDIR=/var/tmp` になった。
- 通知機能（`WEKO_NOTIFICATIONS`）を使う場合は、inbox と mongo が必要。使わない場合は `WEKO_NOTIFICATIONS = False` にする【要確認】。

### 3.5 uwsgi.ini と静的ファイルのボリューム

`uwsgi.ini` はイメージのビルド時に `var/instance/conf/` にコピーされる。
このディレクトリを永続ボリューム（`conf_data`）にしていると、古い `uwsgi.ini` が残る。ボリュームの中身を v2.0.5 のものに置き換えること。
静的ファイルのボリュームも同じで、11 で作り直す。

## 5. 旧環境のキューを処理し切る

旧環境（feature/a11y のコード）が動いているうちに、旧コードで統計とインデクサのキューを処理し切る。
v2.0.5 の RabbitMQ 4.0 は 3.x のデータを引き継がないため、キューは空にしておく必要がある。

旧環境の Pod を指すように `WEKO_MIG_WEB` を設定してから、実行する。

```bash
tools/migration/v2.0.5/migrate.sh drain
```

最後に表示される統計の bookmark（集計済みの日付）は、10 で使う。`${WEKO_MIG_LOG_DIR}/bookmarks.txt` に保存される。
RabbitMQ のキューが空であることを確認する。

```bash
kubectl exec -n <rabbitmq namespace> <rabbitmq pod> -- rabbitmqctl list_queues name messages
```

確認できたら、旧環境の web・worker を停止する。

## 6. WEKO v2.0.5 のイメージを用意する

v2.0.5 ベースの a11y ブランチから、web と nginx のイメージをビルドする。

```bash
docker build -t <image registry path>/release/web-a11y:v2.0.5 .

docker push <image registry path>/release/web-a11y:v2.0.5
docker push <image registry path>/release/nginx-a11y:v2.0.5
```

## 7. Elasticsearch のイメージを切り替える

v2.0.5 は統計に ILM を使う。ILM は OSS 版にはないため、`elasticsearch-oss:6.8.23` から `elasticsearch:6.8.23`（既定ディストリビューション）に切り替える。
バージョンとプラグインは変わらず、データのボリュームはそのまま使える。

一度既定ディストリビューションで起動すると、OSS 版には戻せない（クラスタの状態に ILM の情報が入るため）。2.2 のスナップショットを取ってから切り替えること。
Kubernetes で Elasticsearch を複数機関で共用している場合は、すでに切り替わっているか確認すること【要確認】。

```bash
${WEKO_MIG_WEB} curl -s "http://elasticsearch:9200/?pretty" | grep build_flavor
```

`default` と表示されれば、切り替え済みである。

## 8. PostgreSQL を移行する

v2.0.5 のイメージで **web だけ** を起動する。worker・nginx はまだ起動しない。
worker が先に動くと、統計を書き込もうとして、書き込み先のエイリアスと同じ名前の普通のインデックスが作られてしまう。そうなると、9 で書き込み先インデックスを作れなくなる。

`WEKO_MIG_WEB` を v2.0.5 の web Pod に向けてから、実行する。

```bash
tools/migration/v2.0.5/migrate.sh db
```

`migrate.sh db` は、次のステップを順に実行する。済んだステップは DB のテーブル `weko_upgrade_v205_steps` に記録される。
途中で失敗した場合は、原因を直してから同じコマンドを実行し直せばよい。済んだステップは飛ばされる。

| ステップ | 内容 | 元の手順 |
|---|---|---|

## 9. Elasticsearch を移行する

```bash
tools/migration/v2.0.5/migrate.sh es
```

## 10. 切り替え日の統計の集計をやり直す【要確認】

v2.0.5 では、統計の集計結果の文書 ID が `<id>-<日付>` から `<id>` に変わった。
5 で控えた bookmark の日付の集計結果が、旧形式と新形式の 2 通りで残ると、その日の件数が二重に数えられる。
bookmark の日付の分だけ、集計結果を消してから集計し直す。

```bash
${WEKO_MIG_WEB} invenio stats aggregations delete <集計の種類> --start-date <bookmark の日付>
${WEKO_MIG_WEB} invenio stats aggregations process <集計の種類> --start-date <bookmark の日付> -b -e
```

`delete` は確認を求めてくるので、`-T` や `-i` だけでなく、端末を割り当てて実行すること（`docker compose exec`、`kubectl exec -it`）。
過去の期間をまとめて集計し直すことはしないこと。文書 ID の形式が違うため、二重に数えられる。

## 13. 切り戻す場合

8 以降で問題が起き、切り戻す場合は次の順に行う。

1. v2.0.5 の web・worker・nginx を停止する。
2. PostgreSQL を 2.1 のダンプから復元する。

   ```bash
   pg_restore -U invenio -d <DB 名> --clean --if-exists weko_a11y_before_v2.0.5.dump
   ```

3. Elasticsearch の `<prefix>-*` を削除し、2.2 のスナップショットから復元する。
   - 既定ディストリビューションのままでも、旧コードは動作する見込みである【要確認】。
   - OSS 版に戻すことはできない。
4. 旧イメージ（web-a11y:v0.9.19 など）と旧設定で起動する。

# アップデート処理の流れ

```text
事前確認（migrate.sh preflight）
    ↓
バックアップ（PostgreSQL・Elasticsearch スナップショット・ファイル・設定）
    ↓
設定ファイルの更新（migrate_config.py）※停止前に準備できる
    ↓
メンテナンス開始
    ↓
旧コードでキューを処理し切る（migrate.sh drain）→ 旧環境停止
    ↓
Elasticsearch を既定ディストリビューションへ
    ↓
v2.0.5 の web だけを起動
    ↓
PostgreSQL 移行（migrate.sh db）
    ↓
Elasticsearch 移行・再インデックス（migrate.sh es）
    ↓
切り替え日の統計の集計やり直し
    ↓
静的ファイル（migrate.sh assets）
    ↓
worker・nginx 起動、メンテナンス終了
    ↓
事後確認（migrate.sh verify）と画面での動作確認
```
