# WEKO v1.0.8b から v2.0.0 へのアップデート方法

## docker

本手順は、Docker Compose で構築した単一の WEKO 環境を、v1.0.8b から v2.0.0 へアップデートする場合を対象とする。

JAIRO Cloud 本番環境のような複数機関一括更新、Kubernetes、PgPool、Ingress Controller、fluentd 等のインフラ固有操作は対象外とする。

実際の環境によって以下は異なる可能性があるため、適宜読み替えること。

- Docker Compose ファイル名
- Docker Compose のサービス名
- PostgreSQL の DB 名
- Elasticsearch のインデックス prefix
- `instance.cfg` の環境固有設定
- Shibboleth や S3 等の外部連携設定

以下では Docker Compose ファイルを `docker-compose2.yml` とする。

---

## 1. アップデート前の状態を確認する

まず、現在の WEKO のブランチおよびコンテナ状態を確認する。

```bash
cd /path/to/weko

git status
git branch --show-current
git log -1 --oneline
```

Docker の状態も確認する。

```bash
docker compose -f docker-compose2.yml ps
```

ローカルに未コミットの変更がある場合は、アップデート作業前にコミットまたは `git stash` 等で退避する。

---

## 2. バックアップを取得する

アップデート前に、少なくとも PostgreSQL と WEKO 設定ファイルをバックアップする。

### 2.1 PostgreSQL

```bash
docker compose -f docker-compose2.yml exec -T postgresql \
  pg_dump -U invenio invenio \
  > weko_v1.0.8b_before_upgrade.sql
```

バックアップファイルが作成されていることを確認する。

```bash
ls -lh weko_v1.0.8b_before_upgrade.sql
```

環境によって DB 名が `invenio` ではない場合は読み替えること。

### 2.2 設定ファイル

以下のような環境固有設定をバックアップする。

```bash
mkdir -p backup_v1.0.8b

cp .env backup_v1.0.8b/ 2>/dev/null || true
cp docker-compose2.yml backup_v1.0.8b/
cp instance.cfg backup_v1.0.8b/ 2>/dev/null || true
cp weko.conf backup_v1.0.8b/ 2>/dev/null || true
cp uwsgi.ini backup_v1.0.8b/ 2>/dev/null || true
```

---

## 3. WEKO Web を停止する

データベースマイグレーション中にデータ更新が発生しないよう、WEKO Web を停止する。

```bash
docker compose -f docker-compose2.yml stop web
```

環境全体を停止して問題ない場合は以下でもよい。

```bash
docker compose -f docker-compose2.yml down
```

ただし、PostgreSQL に SQL マイグレーションを実施するため、後続手順では PostgreSQL コンテナを起動しておく必要がある。

---

## 4. WEKO v2.0.0 のソースコードへ更新する

最新のブランチ・タグ情報を取得する。

```bash
git fetch --all --tags
```

v2.0.0 のリリースブランチを使用する場合：

```bash
git checkout release_v2.0.0
```

開発ブランチを使用する場合：

```bash
git checkout develop_v2.0.0
git pull
```

更新後、対象ブランチを確認する。

```bash
git branch --show-current
git log -1 --oneline
```

---

## 5. instance.cfg を v2.0.0 用に更新する

v2.0.0 では設定項目が多数追加されているため、既存の `instance.cfg` と v2.0.0 用設定を比較し、必要な設定を反映する。

既存環境固有の設定を保持するため、`instance.cfg` を一律に上書きしないこと。

元の更新作業でも `instance.cfg` は v2.0.0 用ファイルへ変更されている。

### 5.1 Celery result backend

Redis の DB 番号を固定値ではなく設定値から取得する。

```python
CELERY_RESULT_BACKEND = (
    'redis://{{ environ("INVENIO_REDIS_HOST") }}:6379/'
    + CELERY_RESULT_BACKEND_DB_NO
)
```

### 5.2 Author temporary file cleanup

著者情報の一時ファイルを定期削除する Celery task を追加する。

```python
'remove_author_tmp_file': {
    'task': 'weko_authors.tasks.check_tmp_file_time_for_author',
    'schedule': timedelta(hours=1),
    'args': [],
},
```

### 5.3 Elasticsearch default index

以下を追加する。

```python
INDEXER_DEFAULT_INDEX = SEARCH_INDEX_PREFIX + "weko"
```

### 5.4 S3

S3 compatible storage を使用する場合は以下を確認する。

```python
S3_SECRET_ACCESS_KEY = '{{ environ("S3_SECRECT_ACCESS_KEY") }}'

FILES_REST_LOCATION_TYPE_LIST = [
    ('s3', 'S3 Path'),
    ('s3_vh', 'S3 Virtural Host')
]
```

### 5.5 Restricted Access

Restricted Access 機能を使用する場合は以下を追加する。

```python
WEKO_ADMIN_RESTRICTED_ACCESS_DISPLAY_FLAG = False
```

### 5.6 Author temporary directory

```python
WEKO_AUTHORS_EXPORT_TMP_DIR = '{{ environ("TMPDIR") }}'
WEKO_AUTHORS_IMPORT_TMP_DIR = '{{ environ("TMPDIR") }}'
```

### 5.7 Item update task

```python
WEKO_DEPOSIT_ITEM_UPDATE_TASK_TTL = 60 * 60 * 24 * 30
WEKO_DEPOSIT_ITEM_UPDATE_RETRY_COUNT = 1
WEKO_DEPOSIT_ITEM_UPDATE_RETRY_COUNTDOWN = 3
WEKO_DEPOSIT_ITEM_UPDATE_RETRY_BACKOFF_RATE = 2
```

### 5.8 Search / UI

必要に応じて以下を追加する。

```python
WEKO_SEARCH_UI_FACET_LANG_DISP_FLG = False
DISPLAY_LOGIN = True
WEKO_RECORDS_UI_LANG_DISP_FLG = False
WEKO_THEME_FETCH_SEARCH_FLG = False
```

### 5.9 任意機能

以下は利用環境に応じて設定する。

- researchmap 連携
- OA Assist
- GakuNin RDM
- JGSS 利用申請機能
- Notification
- SWORD
- Redis Sentinel
- Shibboleth

v2.0.0 用設定には、researchmap、OA Assist、JGSS 等の環境依存設定が多数追加されているため、必要なものだけ採用する。

## 6. Shibboleth を使用している場合、weko.conf を確認する

Shibboleth を利用している環境では、`weko.conf` の属性連携設定を確認する。

元の v2.0.0 更新作業では、Shibboleth session 変数名を変更している。

```diff
-shib_request_set $shib_shib_session_id $upstream_http_variable_shib_session_id;
-fastcgi_param Shib-Session-ID $shib_shib_session_id;
+shib_request_set $shib_session_id $upstream_http_variable_shib_session_id;
+fastcgi_param Shib-Session-ID $shib_session_id;

-shib_request_set $shib_shib_session_index $upstream_http_variable_shib_session_index;
-fastcgi_param Shib-Session-Index $shib_shib_session_index;
+shib_request_set $shib_session_index $upstream_http_variable_shib_session_index;
+fastcgi_param Shib-Session-Index $shib_session_index;
```

また、JAIRO Cloud の更新環境では `eppn` として渡す属性を `eppn` から `persistent-id` に変更している。

```diff
-#shib_request_set $shib_persistent_id $upstream_http_variable_persistent_id;
-#fastcgi_param eppn $shib_persistent_id;
+shib_request_set $shib_persistent_id $upstream_http_variable_persistent_id;
+fastcgi_param eppn $shib_persistent_id;

-shib_request_set $shib_eppn $upstream_http_variable_eppn;
-fastcgi_param eppn $shib_eppn;
+#shib_request_set $shib_eppn $upstream_http_variable_eppn;
+#fastcgi_param eppn $shib_eppn;
```

この変更は認証環境に依存するため、すべての環境で一律に適用しないこと。

Shibboleth を使用していない Docker 環境では本手順は不要。

---

## 7. uwsgi.ini を確認する

大容量ファイルのアップロードを使用する場合は `harakiri` の設定を確認する。

元の v2.0.0 更新手順では、大容量ファイルアップロード中に `harakiri` が発動しないよう無効化している。

例：

```ini
# harakiri = 300
```

## 8. Docker イメージを更新する

ソースコードから WEKO の Docker image を作成している場合は再ビルドする。

```bash
docker compose -f docker-compose2.yml build
```

キャッシュを使用しない場合：

```bash
docker compose -f docker-compose2.yml build --no-cache
```

Registry 上の image を利用している場合は、Compose ファイル内の image tag を v2.0.0 用に変更後、以下を実行する。

```bash
docker compose -f docker-compose2.yml pull
```

確認：

```bash
docker compose -f docker-compose2.yml images
```

---

## 9. PostgreSQL を起動する

停止している場合は PostgreSQL を起動する。

```bash
docker compose -f docker-compose2.yml up -d postgresql
```

確認：

```bash
docker compose -f docker-compose2.yml ps
```

---

## 10. PostgreSQL マイグレーションを実行する

v1.0.8b から v2.0.0 への更新では、以下の SQL を実行する。

```text
postgresql/ddl/W2025-29.sql
```

元の更新スクリプトでも、各リポジトリ DB に対してこの SQL を `psql` で実行している。

SQL ファイルを PostgreSQL コンテナへコピーする。

```bash
docker cp \
  postgresql/ddl/W2025-29.sql \
  $(docker compose -f docker-compose2.yml ps -q postgresql):/tmp/W2025-29.sql
```

実行する。

```bash
docker compose -f docker-compose2.yml exec postgresql \
  psql -U invenio invenio \
  -f /tmp/W2025-29.sql
```

ログを保存する場合：

```bash
docker compose -f docker-compose2.yml exec postgresql \
  psql -U invenio invenio \
  -f /tmp/W2025-29.sql \
  2>&1 | tee migration_W2025-29.log
```

エラー確認：

```bash
grep -i error migration_W2025-29.log
```

SQL マイグレーションでエラーが発生した場合は、後続処理を実施せず原因を確認する。

---

## 11. WEKO v2.0.0 を起動する

SQL マイグレーション完了後、WEKO を起動する。

```bash
docker compose -f docker-compose2.yml up -d
```

状態を確認する。

```bash
docker compose -f docker-compose2.yml ps
```

Web コンテナのログを確認する。

```bash
docker compose -f docker-compose2.yml logs --tail=200 web
```

起動時に traceback や設定エラーが発生していないことを確認する。

---

## 12. Python データマイグレーションを実行する

v2.0.0 では SQL マイグレーションに加えて、WEKO アプリケーション側のデータ変換を実施する。

元の `migration_py.sh` で実際に実行している処理は以下。

```bash
invenio shell scripts/demo/update_W2025-29.py 30015 500
```

Docker 環境では Web コンテナ内で直接実行する。

```bash
docker compose -f docker-compose2.yml exec web \
  invenio shell scripts/demo/update_W2025-29.py 30015 500
```

`30015` および `500` は既存の v2.0.0 更新処理で使用している引数のため、そのまま使用する。

処理後、Web のログを確認する。

```bash
docker compose -f docker-compose2.yml logs --tail=300 web
```

---

## 13. Elasticsearch の mapping を更新する

v2.0.0 では著者情報用 Elasticsearch index に `communityIds` フィールドを追加する。

追加する mapping は以下。

```json
{
  "properties": {
    "communityIds": {
      "type": "keyword"
    }
  }
}
```

まず対象 index を確認する。

```bash
docker compose -f docker-compose2.yml exec elasticsearch \
  curl -s localhost:9200/_cat/indices?v
```

対象 index は以下の形式。

```text
<repository-prefix>-authors-author-v1.0.0
```

mapping を更新する。

```bash
docker compose -f docker-compose2.yml exec elasticsearch \
  curl -XPUT \
  "localhost:9200/<repository-prefix>-authors-author-v1.0.0/_mapping/author-v1.0.0?pretty" \
  -H "Content-Type: application/json" \
  -d '{
        "properties": {
          "communityIds": {
            "type": "keyword"
          }
        }
      }'
```

確認：

```bash
docker compose -f docker-compose2.yml exec elasticsearch \
  curl -s \
  "localhost:9200/<repository-prefix>-authors-author-v1.0.0/_mapping?pretty"
```

`communityIds` が `keyword` として存在することを確認する。

---

## 14. Elasticsearch の dynamic mapping timeout を変更する

元の v2.0.0 更新手順では、dynamic mapping の timeout を 600 秒に変更している。

```bash
docker compose -f docker-compose2.yml exec elasticsearch \
  curl -XPUT localhost:9200/_cluster/settings \
  -H "Content-Type: application/json" \
  -d '{
    "persistent": {
      "indices.mapping.dynamic_timeout": "600s"
    }
  }'
```

確認：

```bash
docker compose -f docker-compose2.yml exec elasticsearch \
  curl -s localhost:9200/_cluster/settings?pretty
```

---

## 15. Elasticsearch reindex を実行する

mapping 更新後、既存アイテムを再インデックスする。

まず reindex 対象を登録する。

```bash
docker compose -f docker-compose2.yml exec web \
  invenio index reindex \
  --pid-type recid \
  --yes-i-know
```

続いて index 処理を実行する。

```bash
docker compose -f docker-compose2.yml exec web \
  invenio index run \
  --raise-on-error False \
  --chunk-size 50
```

`--chunk-size 50` は一度に処理する件数を 50 件に制限する。

`--raise-on-error False` により、個別アイテムでエラーが発生しても可能な範囲で処理を継続する。

reindex 中は RabbitMQ および Elasticsearch の負荷を確認する。

```bash
docker compose -f docker-compose2.yml ps
```

Elasticsearch の状態：

```bash
docker compose -f docker-compose2.yml exec elasticsearch \
  curl -s localhost:9200/_cluster/health?pretty
```

## 16. Javascript / static assets を更新する

WEKO の JavaScript / CSS 等の変更を反映する。

```bash
docker compose -f docker-compose2.yml exec web \
  invenio assets build
```

続いて static files を収集する。

```bash
docker compose -f docker-compose2.yml exec web \
  invenio collect
```

必要に応じて Web を再起動する。

```bash
docker compose -f docker-compose2.yml restart web
```

## 17. 動作確認を行う

アップデート後、最低限以下を確認する。

### トップページ

- WEKO トップページが正常に表示される
- HTTP 500 / 502 が発生しない

### ログイン

- 管理者でログインできる
- 一般ユーザーでログインできる

### 検索

- 既存アイテムを検索できる
- 検索結果件数に不自然な差異がない

### アイテム詳細

- アイテム詳細画面が表示できる
- メタデータが正常に表示される
- ファイルがダウンロードできる

### アイテム登録

- アイテムタイプが表示される
- メタデータ登録画面が表示される
- ファイルアップロードができる
- 登録後に検索できる

### アイテム編集

- 既存アイテムを編集できる
- 更新内容を保存できる

### Shibboleth

使用している場合：

- Shibboleth ログインできる
- ユーザー識別子が想定どおり取得される
- `eppn` / `persistent-id` のマッピングが正しい

# アップデート処理の流れ

```text
バックアップ
    ↓
WEKO Web停止
    ↓
WEKO v2.0.0 ソースコード更新
    ↓
instance.cfg / weko.conf / uwsgi.ini 更新
    ↓
Docker image更新
    ↓
PostgreSQL SQL migration
    ↓
WEKO v2.0.0 起動
    ↓
Python migration
    ↓
Elasticsearch mapping更新
    ↓
Elasticsearch dynamic mapping timeout変更
    ↓
Elasticsearch reindex
    ↓
Javascript / static assets更新
    ↓
動作確認
```

# 主要なマイグレーション処理

v1.0.8b から v2.0.0 への更新で、データ移行に直接関係する主要処理は以下。

## PostgreSQL

```bash
psql -U invenio invenio \
  -f /tmp/W2025-29.sql
```

## Python

```bash
invenio shell \
  scripts/demo/update_W2025-29.py \
  30015 500
```

## Elasticsearch mapping

```json
{
  "properties": {
    "communityIds": {
      "type": "keyword"
    }
  }
}
```

対象：

```text
<repository-prefix>-authors-author-v1.0.0
```

## Reindex

```bash
invenio index reindex \
  --pid-type recid \
  --yes-i-know
```

```bash
invenio index run \
  --raise-on-error False \
  --chunk-size 50
```

# 補足

JAIRO Cloud 本番環境の元手順には、以下の処理も含まれている。

- PgPool の設定変更
- PostgreSQL `work_mem` の変更
- NGINX Plus 更新
- Ingress Controller の再デプロイ
- fluentd の再デプロイ
- 複数リポジトリ一括処理
- Kubernetes Pod 単位の処理
- 並列 SQL migration
- 並列 reindex

これらは WEKO v2.0.0 の単一 Docker 環境におけるアプリケーション更新そのものではないため、本手順では対象外とする。
