# リリースに合わせたドキュメント更新の手順

WEKO3 の新しいリリース（例：release_v2.1.0）に合わせて、weko-document のマニュアル・機能仕様書・登録ガイド・英語版マニュアル・アップデート手順書を実装と突き合わせて更新する手順です。v2.1.0（2026年10月）の作業をもとにまとめています。

Claude Code で作業する場合は、同じ手順と依頼文の雛形・スクリプトを `.claude/skills/weko-release-doc-update/` に置いています（「v2.2.0 向けにドキュメントを更新して」のように依頼すると、この手順に沿って進めます）。使い方は「[ドキュメント更新スキルの使い方](release_doc_update_skill.md)」を参照してください。

## 1. 事前に決めること

| 項目 | 説明 | v2.1.0 の例 |
|---|---|---|
| 今回のバージョン | タグや改定履歴に使う | v2.1.0 |
| 実装のリリースブランチ／コミット | 突合の基準 | release_v2.1.0（508030789） |
| 直前のリリースタグ | 「今回の変更」を判定する基準 | v2.0.4 |
| 前回ドキュメントを突合した実装コミット | 差分の棚卸しの起点 | b19e39d8a |
| weko-document の分岐点 | 新バージョンのタグを付ける範囲の起点 | main から分岐した d11f699 |
| 撮影用のローカル環境 | スクリーンショット撮影 | wekov2（release_v2.1.0） |

## 2. 作業の流れ

1. **実装の差分を棚卸しする**
   前回突合した地点からリリースまでのマージ・変更ファイルを一覧にし、テーマ（認可の強化、新機能、設定、DB 移行など）に分けます。
2. **機能仕様書を突き合わせる**（`docs/spec/base`）
   カテゴリごと（api、access_control・restricted_access、admin、ams、user、other・tools・直下）に、権限・応答・処理概要・設定値を実装に合わせます。前回以降に他の人が追記した内容も確認します。
3. **マニュアルを突き合わせる**（`docs/manuals/ADMIN`、`docs/manuals/USER`）
   大きいファイルは章の境目で分割して並行して作業し、最後に結合します。結合後に目次・版数・改定履歴を更新します。
4. **登録ガイドを突き合わせる**（`docs/manuals/GUIDE`）
   改行コードが CRLF のファイルがあるので、改行を保ちます。
5. **アップデート手順書を作る**（`docs/operation/v前版_v新版.md`）
   直前のリリースタグとの実装差分（DB 更新 SQL、Alembic、Elasticsearch、設定、nginx・Dockerfile）から作り、実機で確かめていない手順には【要確認】を付けます。
6. **英語版マニュアルを更新する**（`docs/manuals_en`）
   - 日本語版で直した内容を、英語版の対応する節に反映します。
   - 英語版に無い章・節は、日本語版から英語で書き起こして差し込みます。
   - 章が増えたら、目次・章構成の一覧・表／図番号を振り直します。
7. **新バージョンのタグを付ける**
   分岐点以降の変更のうち、**直前のリリースタグとの実装差分で挙動が変わったもの**にだけ「【v2.1.0】」（英語版は「[v2.1.0]」）を付けます。見出しには付けません。
8. **番号と参照を確認する**
   見出しの文言が変わっていないこと、タグの数、目次の番号の連続とリンク先、本文の節番号参照、表・図番号を確認します。
   あわせて honkit でビルドし、分岐点から増えたリンク切れ・画像の欠落が無いことを確認します（「[ドキュメント更新スキルの使い方](release_doc_update_skill.md)」の 8 節）。
9. **スクリーンショットを撮る**
   撮影用の管理者アカウントでローカル環境を全画面で撮影し、古い画像と同じ赤枠・矢印・番号を新しい画面に描き込みます。比較ページで確認してから差し替えます。
   英語版は画像番号が日本語版と違うので、まず節ごとに日本語版の画像との対応表を作り、英語画面で撮影します。撮影のついでに見つかった英語画面の翻訳漏れは、実装側に報告します。
10. **コミットする**
    カテゴリ単位（`spec(api): …`、`manual(ADMIN): …`、`manual_en(USER): …`、`operation: …` など）でコミットし、push の前にリモートの変更を取り込みます。

## 3. 注意点（v2.1.0 で分かったこと）

- **「今回の変更」は直前のリリースタグと比べて決める。** 前回突合した地点と比べると、v2.0.3／v2.0.4 で既にリリースされた変更が混ざります。ブランチ名（例：「release_v2.0.3(Measures against 502 errors)」）も当てにせず、コミットがタグに含まれるかを確認します。
- **画面のラベルは実際の表示に合わせる。** 翻訳ファイルの訳と画面の表示が違うことがあります（「説明」と直したラベルが実際は「記述」だった）。
- **見出しの文言を変えない。** 見出しにタグや文言を足すとリンク先（アンカー）が変わり、目次やほかのページからのリンクが切れます。
- **同じファイルを複数人（複数のエージェント）で同時に編集しない。** 分割して編集するか、追加分を別ファイルで作ってからまとめて差し込みます。
- **Word から変換した名残に注意する。** 節をまたいだ通し番号の手順（「335.」）や、旧番号での参照（「(5) ファイルを設定する」）が残っています。
- **作業記録はリポジトリに入れない。** 突合のメモ・計画・進捗などは `.gitignore` に入れてあります。
- **実装の不具合が見つかったら、ドキュメントで取り繕わず実装に報告・修正する。** v2.1.0 では nginx の login.py 消失やウィジェット画像の権限エラーが見つかり、実装に修正の PR を出しました。
- **見出しにパス引数 `\<version>` を書かない。** honkit では HTML タグとして扱われ、見出しが崩れてリンクも切れます。`` `/api/<version>/authors` `` のようにバッククォートで囲みます（GitHub のアンカーは変わりません）。ただし `<pid_value>` のように `_` を含むパスは honkit がアンカーから `_` を消すので、見出しの直前に `<a id="…"></a>` を足して補います（スキルの `add_anchors.py`）。
- **未マージの実装 PR を前提に書いた箇所は記録しておく。** PR の内容が変わったら、ドキュメントも戻す必要があります。

## 4. スクリーンショットのサンプルデータ

撮影のためにローカル環境へ登録したデータ（アイテム、インデックス、ロケーション、OAuth アプリ、承認待ちアクティビティなど）は、名前に `screenshot-sample` を付け、作成方法と削除方法を記録します。既存のデータや設定は変更せず、撮影のために変えた設定は撮影後に戻します。
